# Repository operating instructions

Our Jam implementation was authorized on October 10, 2026. Sound Waves names audience contributions, not the app.

- Read README.md, DEVELOPMENT_PLAN.md, PROGRESS.md and the relevant feature specifications before editing.
- Make routine implementation choices autonomously. Sequence dependencies, fix failures and conflicts, chain PRs and merge only with passing required checks and a safe GitHub merge state.
- Keep plans, contracts, architecture decisions, test evidence, deployment procedures and credential requirements self-contained in the repository.
- Follow the user's End-To-End-Everywhere Security Architecture Standard once its exact text has been retrieved. Public content and server-side generation have explicit trust boundaries; never equate TLS with end-to-end encryption.
- Use only project-specific resources and credentials. Do not reuse unrelated project databases, secrets or deployment services. New spending requires authorization.
- Keep Engine Room tracking accurate when connected. Record pending synchronization locally if it is unavailable.
- Do not claim real provider generation, microphone capture, cross-platform support, security compliance, deployment or recovery until the corresponding integration has been tested.
- The multiplayer production application precedes single-user demonstration work. Keep DJ V2 in its own plan.
- Preserve user changes. Keep migrations compatible with rolling deployment; rehearse recovery before risky changes.
- Do not send external messages, create recurring jobs for agent work, or claim background development is continuing without authorization and a running capability.
