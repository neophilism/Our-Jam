# Audience admission and remote listening

New events created through the performer form default to **room-code voting**. The artist sets a code in **Room access & capacity** and announces or prints it at the venue. Until a code is configured, people can join as listeners. Listening, free downloads and feedback do not require a code; listeners can also request verified event email. Artist archives open in listening mode and each event shows its actual voting policy.

The artist can explicitly select **Everyone, including remote fans** before the first round. Existing events and older API clients that omit `admissionMode` keep their open-voting behavior. This compatibility default is deliberate; integrations creating new production rooms should send an explicit policy. The native draft must adopt the new `canContribute` field and code entry before it can ship with restricted events.

Room codes contain 8–24 letters/numbers, ignoring case, spaces and hyphens. They are stored only as salted hashes on the event, never returned in public or operator snapshots, and cannot be retrieved after saving. Choose a hard-to-guess phrase/code, retain it locally for announcements, and replace it if needed. Join attempts are limited per guest session. A shareable code discourages casual remote participation but does not verify location or one-human-one-vote. New guest identities can bypass identity-based limits; stronger admission would need another identity mechanism.

Contributing requires event membership plus either open voting or prior successful code admission. Both Sound Wave submission and allocation enforce this on the server. Joining as a listener does not grant voting access. Guests can later upgrade using the code. Replacing a code affects new arrivals; already admitted contributors retain access and their existing points. Voting policy and contributor capacity cannot change after the first round begins, so rule changes do not strand live ballots. Code replacement remains available during the show.

Capacity is 1–100 guest contributor identities per event, separate from the number of visible Sound Waves and from listener memberships. Admission locks the event and checks the count before inserting or upgrading membership. Concurrent requests cannot oversubscribe the last place, and existing contributors can rejoin a full room. Capacity cannot be lowered below the contributors the chosen policy already admits. A full event still exposes free music and feedback. The cap does not itself prove acceptable playback, API or venue-network performance for 100 people.

Configure using `PATCH /api/operator/events/:id/admission` with `commandId`, `expectedRevision`, `mode`, `limit` and optional `roomCode`. The route requires the owning operator and exact Origin; command retries are idempotent. `POST /api/events/:slug/join` accepts an optional `roomCode`. Public event state adds `canContribute` and a nonsecret `admission` summary. An old client may show unavailable controls but cannot bypass server enforcement.

Migration 007 adds hash/salt fields and a membership admission flag. It was rehearsed on the isolated development branch; production remains untouched. Readiness requires migrations 001–007. Old application instances ignore this policy: drain them before enabling restricted voting, and do not roll back to an unenforcing version while any restricted event is active. Rollback must keep affected events out of live use until admission enforcement is restored.

Tests cover listener separation, wrong codes, hash omission, simultaneous last-place admission, 105 concurrent requests for 100 slots, repeat admission, owner/Origin gates, frozen policy and vote preservation after code rotation. Desktop/mobile Chromium coverage exercises artist setup, listener-first access, rejected and accepted codes and a real contribution. Physical phone, venue-network and full voting/streaming load acceptance remain open.
